SimAutomate5 code review

A findings-first review of the Tauri desktop application that exchanges ASTM and HL7-style traffic over TCP.

Scope: Rust backend, Vanilla JS frontend, transport, queue, logging, auto-response, configuration Findings: 10 Application source changed: no

Executive summary

The most important risks are operational rather than cosmetic. TCP chunks are treated as complete messages, and automatic responses share an ACK-gated queue with ordinary traffic. Independently, connection tasks can leave stale manager state or clean up a newer connection after a reconnect.

These defects can cause dropped or malformed messages, protocol deadlocks, and connections that appear active but no longer process traffic. The application is not ready for unattended use until the four high-severity findings are addressed.

Overall risk High: reliability and protocol handling are coupled

The existing test suite covers auto-response construction but not the transport, lifecycle, or queue paths where the largest failures occur.

Findings

1. TCP read boundaries are incorrectly treated as message boundaries

High

The read loop passes each arbitrary TCP read directly to message handling. TCP is a byte stream: one MLLP or ASTM message may be split across reads, and multiple messages may arrive in a single read. Exact ACK detection can miss coalesced ACKs, while auto-response parsing can fail when the MSH or control ID is split across chunks.

Evidence
src-tauri/src/transport.rs:438-443 reads into a fixed buffer and immediately calls handle_received_message with the chunk; no receive buffer or MLLP/ASTM frame parser is present.
Impact
Valid traffic can be dropped, misclassified, or displayed as fragments. ACK-gated sending can then stall indefinitely.
Remediation
Maintain a per-connection receive buffer, parse complete MLLP and ASTM frames, dispatch every complete frame, and retain incomplete trailing bytes for the next read. Add split-frame and coalesced-frame tests.

2. Automatic responses can deadlock behind the outbound ASTM ACK gate

High

The sender refuses to release any queued message while waiting_for_ack is true. Automatic responses are appended to that same ordinary queue. If the peer is waiting for an automatic ACK while this application is waiting for an ACK to its own frame, the required response cannot be sent. Ordinary pending user messages can also delay a protocol response.

Evidence
src-tauri/src/message_queue.rs:71 blocks release while waiting for an ACK; src-tauri/src/message_queue.rs:152 enqueues generated responses through the same path.
Impact
Protocol peers can wait on each other indefinitely, especially under simultaneous traffic or when an ASTM segment requires an ACK.
Remediation
Give protocol control responses a priority queue or an independent send path that bypasses the user-message ACK gate. Test simultaneous inbound and outbound protocol traffic.

3. Failed connection attempts leave the manager in a permanently stale Started state

High

The manager stores Connection::Started before the spawned task has connected. Client connection failure and server bind or accept failure return from the task without clearing that manager state or updating its shared status channel to a terminal error. A later Connect command can therefore be rejected as already connecting or already connected.

Evidence
src-tauri/src/transport.rs:128 stores the started connection; failure paths return at src-tauri/src/transport.rs:206 and src-tauri/src/transport.rs:280. The next connect consults the stale state at src-tauri/src/transport.rs:50.
Impact
The UI can remain stuck until an extra disconnect cycle, and users cannot reliably retry after a connection or bind error.
Remediation
Use one cleanup path for every terminal task outcome. Clear the manager's active connection and update the watch status to Error or Disconnected before returning.

4. Reconnecting can cause the old task to shut down the new connection

High

Disconnect replaces the manager state and sends a shutdown request without waiting for the old task to finish. When that task later emits its disconnect event, the emitter unconditionally calls shutdown_now on the connection currently stored in the manager. A reconnect that wins the timing race can therefore be terminated by stale cleanup from the previous connection.

Evidence
src-tauri/src/transport.rs:161 replaces state and signals the old task; src-tauri/src/emitter.rs:87 shuts down whatever connection is current when old-task cleanup runs.
Impact
Intermittent reconnect failures, unexpected disconnects, and difficult-to-reproduce loss of an otherwise healthy new session.
Remediation
Await the old task before establishing a new one, or attach a generation or connection ID to cleanup and only clear the state owned by that task.

5. Notification failure can panic the connection task

Medium

The successful connection path calls the desktop notification integration, and the fallible notification result is unwrapped. Denied permission or an unavailable OS notification service can panic the detached connection task immediately after the socket connects. The manager can then retain stale state while its read and write loops are gone.

Evidence
src-tauri/src/transport.rs:223 calls notification after reporting Connected; src-tauri/src/emitter.rs:97 ends the notification chain with unwrap().
Impact
A nonessential UI integration can terminate network processing and compound the stale-state defect.
Remediation
Handle notification errors as warnings and continue the connection. Keep optional desktop integration outside the failure domain of the network task.

6. Network-triggered responses and frontend history are unbounded

Medium

The outbound queue has no capacity limit, and every generated automatic response is appended to it. In server mode the listener is intentionally exposed on all interfaces, so a reachable peer can send valid messages faster than the sender drains them. The frontend also appends every received message indefinitely.

Evidence
src-tauri/src/message_queue.rs:60 grows pending_messages without a bound; src-tauri/src/message_queue.rs:152 adds each automatic response; src-tauri/src/transport.rs:274 binds 0.0.0.0; src/messages.js:102 appends history without a retention policy.
Impact
Memory growth can degrade or terminate the desktop process during sustained or adversarial traffic.
Remediation
Bound outbound queue and visible history sizes, define overflow behavior, and apply protocol-aware backpressure or rate limiting.

7. Remote HL7 control IDs can inject application control tokens into generated ACKs

Medium

The incoming MSH-10 control ID is interpolated into a human-readable ACK template. The complete response is then passed through the token decoder. A remote control ID containing a literal token such as <FS> or <CR> is converted into a framing byte, allowing the peer to alter the generated response structure.

Evidence
src-tauri/src/auto_response.rs:141 copies the remote control ID into the response; src-tauri/src/message_queue.rs:61 sends the response through translate::to_bytes.
Impact
Malformed ACK framing or message splitting can be induced by crafted but syntactically accepted remote data.
Remediation
Construct response bytes structurally, or validate and escape field data before inserting it into the tokenized representation.

8. Non-ASCII message content is silently corrupted

Medium

Ordinary Rust characters are narrowed to one byte during encoding, while received bytes are converted directly to characters rather than decoded as UTF-8. Accented names and other non-ASCII text therefore cannot round-trip correctly. The documentation describes plain text but does not state an ASCII-only contract.

Evidence
src-tauri/src/translate.rs:95 casts each character to u8; src-tauri/src/translate.rs:110 casts each byte to char.
Impact
Message content can be silently changed in transit or in the UI, creating data integrity problems.
Remediation
Preserve UTF-8 bytes consistently, or explicitly reject and document non-ASCII input if the supported protocols are intentionally ASCII-only. Add round-trip tests.

9. Every rendered message raises a JavaScript exception

Low

The message is appended before the final logging call, so display generally succeeds, but each event then references undefined direction and logInfo. This creates a runtime exception for every rendered message and means frontend logging never runs.

Evidence
src/messages.js:105 calls logInfo(... direction ...); neither symbol is defined elsewhere in the workspace according to the review search.
Impact
Browser console noise and lost diagnostic logging make real frontend failures harder to detect.
Remediation
Use the existing message type value and implement the log_frontend bridge, or remove the call until a defined helper is available.

10. Server connection fields are not disabled while connected

Low

The code correctly queries the client form, but the server field query is made on serverModeBtn, the mode button, rather than on the selected serverForm. The selector therefore finds no fields, leaving the server port editable during connection attempts and active connections.

Evidence
src/connection-options.js:57 calls serverModeBtn.querySelectorAll(...) after creating serverForm.
Impact
The UI can imply a port change is active when the backend is still listening on the original port, violating the stated configuration contract.
Remediation
Query serverForm.querySelectorAll(...) and add a UI test covering both client and server mode while connecting and connected.

Assumptions and residual risk

Contract-dependent items

  • Binding the server to 0.0.0.0 is explicitly required by the specification, so the unauthenticated cleartext listener was treated as an accepted deployment risk rather than a separate finding. It should be restricted to an isolated test network or protected with host and firewall controls.
  • Raw protocol payloads are intentionally logged because this application is used for internal debugging. That choice is accepted for the stated deployment context and was removed from the actionable findings; it would need to be revisited before shared, unattended, or sensitive-data use.
  • The non-ASCII finding assumes documented plain-text inputs are expected to support Unicode. If the protocol contract is ASCII-only, validation and documentation should make that explicit.

Defense in depth

  • src-tauri/tauri.conf.json:21 disables CSP. This was not counted as an independently exploitable finding because the current frontend uses textContent for message data and no direct untrusted HTML sink was found.
  • A strict local CSP would still reduce the impact of future injection regressions and should be considered after the protocol and lifecycle issues are fixed.

Coverage gaps

  • Recommended next test slice: extract a frame parser and queue state machine into testable units, then add integration tests using fragmented and coalesced reads plus connection failure and reconnect scenarios.

Suggested order of repair

  1. Stop logging raw message content and add a redaction regression test.
  2. Implement protocol-aware receive framing and test split/coalesced traffic.
  3. Separate control responses from the user queue and test ACK ordering.
  4. Centralize connection task cleanup, make cleanup generation-aware, and make notification failure nonfatal.
  5. Add bounded queues/history and explicit input encoding rules, then address the frontend and configuration defects.
